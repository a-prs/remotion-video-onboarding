# remotion-video-onboarding — от пустой машины до первого смонтированного видео

Ты ведёшь диалог, а не выполняешь разовую команду. Пользователь может быть человеком, который
никогда не открывал терминал — веди его по шагам ниже **по порядку**, объясняя коротко, что и
зачем происходит, не грузя техническими деталями сверх необходимого. Если пользователь явно
говорит «просто ставь всё и не спрашивай» — можно ускориться, но шаги 2 (риск для системы), 4
(цвета И шрифт — оба, не только цвета), 5 (режим графики — авто/без/сам продиктую, и оценка
времени перед стартом), 6 п.2 (поиск дублей/фальстартов — это инлайн-рассуждение без скрипта,
его легче всего молча пропустить, а на выходе получится «дубли не вырезаются»), 6 п.7
(реализация графики по выбранному режиму) и 7 (итоговый отчёт + превью + подтверждение перед
финальным рендером — не рендери молча сразу после графики) всё равно нельзя пропускать молча, см.
почему в этих шагах.

## Шаг 0. Определи платформу и агента

Одно и то же — на Claude Code (терминал), Claude Desktop (вкладка **Code**, не Chat и не
Cowork — в тех проектные скиллы не видны) и на Codex. Если это Codex — сразу читай
`references/codex.md`, там свой путь установки скилла (формат `SKILL.md` тот же, но раскладка
другая) и важное ограничение: у Codex нет браузерной панели превью, рендер придётся смотреть
через `localhost` в обычном браузере пользователя, а не внутри агента.

**Если это Claude Desktop, но у тебя нет доступа к файловой системе/терминалу** — это значит,
что сообщение отправили во вкладку Chat или Cowork, а не Code (в Chat нет доступа к файлам
вообще, пользователь мог просто вставить этот промпт текстом не в ту вкладку). Не пытайся
выполнять шаги ниже. Скажи прямо первым же сообщением: «этот скилл работает с файлами на диске
— переключись на вкладку **Code** (сверху по центру окна Desktop), там выбери Local → Select
folder и укажи (или создай новую) пустую папку под проект, и уже там пришли это же сообщение
снова». Продолжай только после того, как убедился, что находишься в Code (виден доступ к
файлам/bash).

## Шаг 0.5. Проверь, не вышла ли новая версия скилла

**В начале КАЖДОЙ сессии** (не только при первой установке) сверь версию: прочитай локальный
файл `VERSION` (лежит рядом с этим `SKILL.md`, в папке установленного скилла), затем попробуй
получить актуальный `https://raw.githubusercontent.com/a-prs/remotion-video-onboarding/main/VERSION`
(сначала через WebFetch, если недоступен — `curl -fsSL <url>`). Это best-effort проверка — если
сети нет/запрос не прошёл, просто молча продолжай, не блокируй пользователя и не жалуйся на ошибку.

Если версии совпали — ничего не говори, иди дальше молча. Если удалённая версия ДРУГАЯ — скажи
пользователю коротко (одной репликой, не в начале длинной простыни): «вышла новая версия скилла
(у тебя X, актуальная Y) — обновить: `npx skills add a-prs/remotion-video-onboarding --skill '*'
--agent claude-code -y`», и подтяни `CHANGELOG.md` тем же способом (WebFetch/curl тот же URL,
файл `CHANGELOG.md` вместо `VERSION`) — прочитай верхнюю запись(и) и скажи пользователю СВОИМИ
словами коротко, что поправили (не выгружай весь файл целиком). Не заставляй обновляться —
предложи и продолжай текущей (локальной) версией, если пользователь не попросил обновить прямо
сейчас: середина монтажа — не время рвать сессию ради апдейта.

## Шаг 1. Проверь окружение, поставь то, что безопасно ставить без вопросов

Всё через `npx` (Node-пакеты, никакого sudo, ставится в пределах пользовательской папки) —
ставь сразу, не спрашивая лишний раз:
- Node.js 18+ — если его нет вообще, это единственное, что нужно от пользователя поставить
  руками (обычный инсталлятор с nodejs.org) — ты не можешь поставить сам интерпретатор.
- Проект Remotion: `npx create-video@latest --yes --blank my-video && cd my-video && npm install`
  — если текущая папка уже внутри git-репозитория, эта команда упадёт: создай `my-video` в
  отдельной пустой папке вне git.
- Официальный набор скиллов: `npx skills add remotion-dev/skills --skill '*' --agent claude-code -y`
  (флаги обязательны — без них команда интерактивная и без TTY зависнет). Ставится в
  `./.claude/skills/` внутри проекта — если сессия уже была открыта в этой папке, перезапусти её.
- FFmpeg/ffprobe — сами скачаются при первом реальном вызове `npx remotion ffmpeg/ffprobe`,
  прогревать заранее не нужно (в отличие от браузера ниже, отдельной команды прогрева для них нет).
- Headless-браузер для рендера: `npx remotion browser ensure` — прогрей сразу, иначе первый
  реальный рендер скачает ~150 МБ Chrome Headless Shell и может упасть 403 за корпоративным
  прокси/в закрытом контуре (тогда — `--browser-executable=<путь к своему Chrome>`).
- Whisper для субтитров: `npx remotion add @remotion/install-whisper-cpp` (не `npm install` —
  версия должна остаться в связке с остальными `@remotion/*`-пакетами, иначе может разъехаться).
- **`numpy`/`scipy` (Python) — нужны на ЛЮБОЙ ОС, не только на Linux**: `scripts/clean_audio.py` и
  `scripts/vad.py` (Шаг 6) на них завязаны, `pip install numpy scipy` — это всё, что нужно
  (никакого torch/нейросетевых моделей, осознанное решение — `references/audio-pipeline.md`).
  `clean_audio.py` без них деградирует мягко (`cut_silence.py --level` тихо пропустит выравнивание
  голоса, там есть try/except; отдельный вызов `clean_audio.py <video> --render <out>` на Шаге 6
  п.6 упадёт голым traceback) — но **`vad.py` без numpy/scipy падает жёстко** (нет fallback), а
  без него нет входа для `refine_cuts.mjs` на Шаге 6 п.3 — проверь заранее, не жди, пока
  пользователь наткнётся на это сам.

Полный список платформенных нюансов (не только Linux) — `references/os-install.md`: apt-либы для
headless-браузера — Linux-специфика, но есть и общий раздел про звук, тот же выше по пунктам —
прочитай файл целиком, а не только Linux-часть, независимо от ОС пользователя.

**Правило: перед КАЖДОЙ тяжёлой закачкой — скажи, что качаешь, сколько весит и разово это или
нет.** Пользователь не должен просто смотреть на зависший терминал, не понимая, происходит что-то
нормальное или скилл завис. Одна короткая фраза перед стартом: «качаю headless-браузер для рендера
(~150 МБ) — это разово, дальше будет закэширован» / «качаю модель распознавания речи (~1.5 ГБ,
разово, дальше переиспользуется в этом проекте) — на медленном интернете может занять несколько
минут». Касается любой закачки за пределами `npm install` пакетов (тот и так печатает прогресс
сам): headless-браузер, whisper-модель (Шаг 6.1 — самая тяжёлая по объёму), ffmpeg/ffprobe.

## Шаг 2. Спроси разрешение отдельно на всё, что трогает систему целиком

Если понадобится `apt install` (Linux, системные библиотеки для headless-браузера) —
**спроси в диалоге явно**, не полагайся только на то, что харнесс и так спросит подтверждение
команды. Пользователь может быть в режиме автоодобрения команд и не осознавать, что скилл про
монтаж видео сейчас полезет ставить системные пакеты на его машину. Одна фраза достаточно:
«для рендера видео на Linux нужно поставить N системных библиотек через apt — ставлю?» — и жди
ответа, прежде чем выполнять.

Если что-то из установки упало на середине (сеть, нет прав) — не начинай с нуля: сам проверь, что
уже стоит (нет отдельного скрипта/тула под именем «detect_env» — это твоя обычная проверка, не
вызов чего-то готового), и продолжи только с недостающего. Скажи пользователю, что конкретно не
встало и что сделать руками, если автоустановка не может.

## Шаг 3. Объясни официальный набор скиллов — ты дирижёр над ним, не замена

Официальный `remotion-dev/skills` — это 12 скиллов, и пользователю не нужно самому лезть в
документацию Remotion, чтобы понять, какой когда нужен. Коротко объясни (не грузи все 12 сразу
списком — упомяни по ходу дела, когда реально понадобится):

- `/remotion-create` — новый проект/композиция.
- `/remotion-markup` — разметка сцены: анимации, типографика, медиа.
- `/remotion-render` — рендер в видео/стилл.
- `/remotion-captions` — субтитры (сам транскрипт не делает без whisper-cpp, см. Шаг 1).
- `/remotion-studio` — локальный превью-сервер.
- `/remotion-best-practices` — используй как общий ориентир, если не уверен, какой из
  остальных скиллов нужен именно сейчас.
- `/remotion-docs`, `/remotion-upgrade`, `/remotion-maps`, `/remotion-saas`,
  `/remotion-interactivity`, `/remotion-multimedia` — служебные, включай по ходу задачи, если
  она реально их касается (карты, апгрейд версии, интерактив и т.д.) — не обязательны для
  обычного монтажа одного ролика.

## Шаг 4. Стайлкит + мини-экскурс возможностей — спроси стиль И шрифты, НЕ дефолти в клише

**Сначала проверь, не настроен ли стиль уже** — открой `assets/stylekit.ts` и посмотри, есть ли
в шапке файла фраза «ships with example values»/«do not ship these example values as-is». Если
она ЕСТЬ — стиль ещё не задан, спрашивай как обычно (см. ниже). Если её НЕТ (значит прошлая
сессия в этом же проекте уже прогнала этот шаг и убрала её при записи финальных значений, см.
ниже) — **не спрашивай заново и не перерисовывай цвета/шрифты** каждый раз, когда монтируешь
новое видео в том же проекте: коротко подтверди («вижу, стиль уже настроен — цвет X, шрифт Y,
используем его?») и иди дальше. Не молчаливо, но и не полным повторным интервью.

**Этот шаг нельзя пропускать молча** (как шаги 2, 5, 6 п.2 и 6 п.7, см. вступление выше) — даже если
пользователь сказал «ставь всё и не спрашивай», цвета и шрифты спроси явно одной короткой фразой,
не дефолти в тишине.

Спроси: «какие цвета хочешь для графики в видео? Если нет идеи — пришли 1-2 референсные картинки
(скриншот бренд-гайда, любимый сайт, любая картинка с нужным настроением), я вытащу оттуда
палитру». Если пользователь прислал картинки — посмотри на них (у тебя есть зрение, отдельный
инструмент не нужен) и вытащи 2-3 реальных hex-цвета, которые в них доминируют.

**Отдельно спроси про шрифт** — это легко забыть, если вопрос про цвета и шрифты слить в одну
фразу вскользь, поэтому задавай его явно: «какой шрифт хочешь для заголовков/подписей? Можно
название реального Google Font, можно «на твой вкус»». Если ответа нет или пользователь не
против дефолта — **Montserrat (текущий дефолт) это нормально оставить**, но сам вопрос задать
обязательно, не просто молча оставить дефолт.

Если пользователь совсем без мнения и без референсов на цвет — **не дефолти в фиолетовый
градиент**, это самый узнаваемый штамп «сгенерировано ИИ». Дефолт — тёмно-графитовый фон
(`#16181d`) + один спокойный акцент (терракот `#c9704f` или тёмная бирюза `#2f7a78`), плоские
заливки, без градиентов и свечения вообще.

Возьми `assets/stylekit.ts` как шаблон (там уже расписано, какие поля обязательны — их читают
все компоненты банка примитивов) и перезапиши `colors` под то, что выяснил — это простая замена
значений, форму объекта не трогай. **Заодно убери из шапки файла фразу про «TEMPLATE»/«ships with
example values»/«do not ship these example values as-is»** (замени на короткую заметку, что стиль
настроен под конкретный проект) — это и есть метка «стиль уже задан» для проверки в начале этого
шага, без неё следующая сессия не поймёт, что переспрашивать не нужно.

**Шрифт — это НЕ простая замена значения**, в отличие от цветов: `style.fonts.heading` и т.д.
получаются из `loadFont()` конкретного пакета `@remotion/google-fonts/<Name>` (см. импорты вверху
`stylekit.ts`), а не пишутся строкой напрямую. Чтобы реально сменить шрифт под ответ пользователя:
1. Найди нужный шрифт в каталоге `@remotion/google-fonts` (пакет называется по имени шрифта,
   например `@remotion/google-fonts/Inter`) — если пользователь назвал шрифт не из Google Fonts
   или которого там нет, честно скажи и предложи ближайший похожий.
2. **Проверь поддержку кириллицы обязательно, не «если будет время»** — если ролик на русском, не
   у каждого Google Font она есть, и это легко пропустить, полагаясь на глаз. Точный способ (в
   пакете 1852 шрифта, кириллица видна прямо из его файла):
   ```js
   const src = fs.readFileSync(
     "node_modules/@remotion/google-fonts/dist/cjs/<Name>.js", "utf8");
   const hasCyrillic = src.includes("cyrillic");
   ```
   Если нет — предупреди пользователя и оставь Montserrat для кириллического текста (он кириллицу
   поддерживает гарантированно), можно применить новый шрифт только к латинским элементам (как уже
   сделано с `PIXEL`/Silkscreen в файле). Отдельно — если пользователь называет коммерческий шрифт
   из своего бренд-гайда (например FreightNeo Pro, Quasimoda), его в `@remotion/google-fonts`
   скорее всего нет вообще: честно скажи и предложи ближайшую бесплатную замену с полной
   кириллицей — засечные: Literata, PT Serif, Merriweather, Spectral, Lora; гротески: Manrope,
   Jost, Onest, Golos Text, Nunito Sans.
3. **Проверь доступные начертания, не только наличие шрифта.** Стайлкит просит
   `headingWeight: 900` — у многих шрифтов максимум 700-800, и браузер в этом случае молча
   «синтезирует» жирность (искажённо утолщает существующее начертание вместо настоящего жирного) —
   в рендере это видно, в коде никакой ошибки не будет. Проверь реальный список весов у выбранного
   шрифта перед тем, как обещать 900 в стайлките, и подстрой `headingWeight` под то, что шрифт
   реально поддерживает.
4. Замени `import { loadFont as loadSans } from "@remotion/google-fonts/Montserrat"` на нужный
   пакет, оставь структуру `loadFont(...)` и имена экспортов (`SANS`/`style.fonts.heading` и т.д.)
   как есть — меняется только ЧТО загружается, не форма объекта `style`.

**Проверь читаемость визуально после смены шрифта, не только на слух.** Разные шрифты сильно
отличаются по ширине символов/кириллице — то, что помещалось в карточку на Montserrat, может не
влезть на другом шрифте и обрежется/наедет на рамку. После первого рендера с новым шрифтом
(Шаг 7 — превью) явно посмотри на карточки/подписи, которые реально попали в этот ролик — не
вылезает ли текст за края, не наезжает ли на рамку карточки. Если видишь обрезание — либо
уменьши размер шрифта в конкретном примитиве, либо предупреди пользователя, что с этим шрифтом
конкретная фраза не помещается и предложи короче.

**Правило без исключений: ЛЮБОЙ примитив (из банка ИЛИ нарисованный с нуля) обязан брать
цвета/шрифты из `style.colors.*`/`style.fonts.*` (`assets/stylekit.ts`), а не хардкодить хекс/имя
шрифта напрямую.** Банковые компоненты уже так устроены — но когда рисуешь НОВЫЙ компонент с
нуля под конкретный запрос (см. правило про банк ниже), легко забыть об этом и вписать цвет
прямо в JSX. Если так сделать — новый компонент не подхватит текущую палитру/шрифт и будет
выбиваться из остальной графики в ролике, а при следующей смене стиля (другой проект/другой
цвет) — не обновится вместе со всеми. Импортируй `style` из `../stylekit` в КАЖДОМ новом файле.

## Мини-экскурс: что вообще можно попросить

Прежде чем переходить к видео — коротко объясни пользователю, что тут вообще можно строить, а не
жди, пока он сам догадается спросить (он может не знать, что возможно в принципе):
- **Готовые интерфейсы/карточки/графики** — из банка (`references/primitive-map.md`): терминал,
  переписка с ИИ, счётчики/графики/диаграммы, зачёркивания и вердикты, цитаты и т.д.
- **Кастомная графика с нуля** — если в банке нет нужного (браузерное окно, телефонный мессенджер,
  дашборд — таких заготовок сейчас нет), можно нарисовать новый компонент под конкретный запрос:
  «опиши, как ты это видишь, или пришли референс (скриншот/схема) — попробую отрисовать».
- **Целая сцена**, а не один элемент — можно попросить собрать составную сцену из нескольких
  примитивов вместе (не только один блок за раз).
- **Динамический фон** из цветных пятен/градиента — это НЕ готовый компонент в банке сейчас,
  но Remotion умеет такое рисовать с нуля так же, как и остальную графику.
- **Куда садится графика** — три варианта, спроси, что нужно: оверлеем поверх видео (лицо видно),
  отдельным сегментом ролика (видео на паузе/скрыто на это время), или вместо видео целиком
  (заменяет кадр, а не дополняет).

## Шаг 5. Первое видео — спроси, где лежит, про графику, предупреди о времени/расходе

Спроси, куда положить исходник (или можно перетащить файл прямо в чат).

**Обязательно спроси про графику ЗДЕСЬ, до начала обработки** — не жди Шага 6 п.7, пользователь
должен выбрать заранее, а не получить сюрприз в конце. Три варианта, спроси прямо:
1. **Автоматически** — ты сама прогонишь расшифровку через банк примитивов и предложишь 1-3
   места (это то, что делает Шаг 6 п.7 по умолчанию — короткая, урезанная версия нашего
   внутреннего арт-директора: не полноценный отдельный скилл, просто «есть банк примитивов,
   найди наиболее подходящий под кусок мысли»).
2. **Без графики вообще** — чистый монтаж (паузы+субтитры+звук), без вставок. В этом случае
   пропусти Шаг 6 п.7 целиком, не предлагай графику молча «на всякий случай».
3. **Пользователь диктует сам** — он говорит, что и когда показывать, ты собираешь и потом
   реализуешь. Если выбрали этот вариант — см. правило ниже про приём по кусочкам.

### Если пользователь диктует сам — принимай по кусочкам, не жди одного большого сообщения

Пользователь может присылать идеи по одной, много мелких сообщений подряд, а не единым
списком. **После КАЖДОГО такого сообщения** — коротко подтверди («ок, принято») и спроси «что-то
ещё?», добавляя пункт в накапливаемый список требований по монтажу (место в ролике + что
показать). Не переходи к реализации, пока пользователь явно не скажет, что список закончен.
Для каждого пункта — если он ложится на существующий примитив банка, используй его; если нет —
это создание нового компонента с нуля (см. правило «новый примитив — всегда предлагай занести
в банк» ниже, оно применимо и здесь).

Перед тем как запускать тяжёлую обработку — проверь длительность (`ffprobe`) и, если файл длинный
(по ощущению — от 30-40 минут), явно предупреди: «файл на N минут, обработка (транскрипция+рендер)
займёт примерно столько-то и заметно потратит дневной лимит — продолжаем или сначала возьмём
кусок покороче для теста?». Не запускай тяжёлый пайплайн молча на файле любого размера.

**Перед стартом Шага 6 — дай общую оценку времени и предупреди не закрывать сессию.** Когда все
требования собраны (видео есть, стиль/шрифт выяснены на Шаге 4, режим графики выбран выше) —
одной фразой оцени, сколько уйдёт на весь пайплайн целиком (транскрипция + вырезание пауз +
графика + рендер, плюс разовая закачка моделей при первом запуске, если ещё не прогревал по
Шагу 1) — диапазоном, не точной цифрой («на глаз, минут 10-20, если модели уже скачаны, при
первом запуске может быть дольше»), и явно попроси не закрывать ноутбук/сессию, пока работаешь:
«не закрывай сессию, я пошёл обрабатывать — вернусь с результатом примерно через N». Потом уже
приступай.

## Шаг 6. Обработка — по порядку, ничего не пропускать

1. **Транскрипция — спроси движок, если ещё не спрашивал в этом проекте.** Проверь маркер
   `transcription-engine:` в шапке `assets/stylekit.ts` (та же механика, что `retake-review`/
   `final-review`). Если не спрашивали (дефолт `local`, ещё не подтверждён явно) — спроси коротко:
   «транскрипция локально (whisper.cpp, офлайн, бесплатно) или через Groq API (быстрее, заметно
   точнее на русском, но нужен свой `$GROQ_API_KEY` и это платно — идёт с твоих кредитов Groq,
   аудио уходит в их облако)?» — и запиши ответ в `transcription-engine: local|groq`, дальше в этом
   проекте не переспрашивай. Если пользователь выбрал `groq`, но `$GROQ_API_KEY` не задан в
   окружении — скажи прямо, что переменная не найдена, и попроси задать её в СВОЁМ терминале
   (`export GROQ_API_KEY=...`) — **никогда не проси прислать ключ текстом в чат** и никогда не
   печатай его значение, даже частично.

   **Перед вызовом любого движка — проверь долю тишины, если файл длинный (>5 минут).** Whisper
   зацикливается на длинных беззвучных участках (не баг, известное поведение) — на реальном ролике
   9:43 с 81% тишины локальный `medium` выдал ~70 повторов одного предложения от середины до конца.
   `scripts/prep_speech_only.py <video> workDir/speech.wav workDir/speech_map.json` — если тишина
   выше ~55%, склеивает только речевые участки С ЗАПАСОМ контекста и выходит с кодом 0
   (транскрибируй `workDir/speech.wav` вместо оригинала, потом `scripts/remap_words.py
   words_spliced.json workDir/speech_map.json words.json` вернёт тайм-коды на оригинальный
   таймлайн); если тишины немного — выходит с кодом 2, ничего не создаёт, транскрибируй оригинал
   как обычно. Подробнее и почему нельзя просто транскрибировать уже смонтированный файл (другая,
   более грубая ошибка) — `references/audio-pipeline.md`.
   - **`local`** — `@remotion/install-whisper-cpp` с `tokenLevelTimestamps: true` и флагом `--dtw`
     — без них не будет word-level тайм-кодов, а они нужны на следующем шаге. **Модель —
     ОБЯЗАТЕЛЬНО без суффикса `.en`** (`model: "medium"`, не `"medium.en"`): пакет по умолчанию
     ставит `medium.en`, а это **англоязычная модель** — на русской (или любой нерусской) речи она
     либо не распознает вообще, либо даст мусор, и субтитры/текст будут рваными независимо от
     всего остального в этом файле. Модели БЕЗ суффикса — многоязычные. Спроси пользователя, на
     каком языке речь в видео (или посмотри на язык переписки в чате — обычно достаточно), и
     передай `language` соответствующим кодом (`ru` и т.д.). Перед закачкой скажи размер (`medium`
     ~1.5 ГБ, разово) — см. правило про закачки в Шаге 1; если пользователь торопится/делает
     быстрый тест — предложи `small` (~488 МБ, быстрее, чуть менее точная) как осознанный
     компромисс, не молчаливый дефолт. **`toCaptions()` на русском отдаёт подсловные BPE-токены**
     (`тест|ов|ый`, не «тестовый») — обязательно склей их по ведущему пробелу токена в целые слова
     перед тем, как писать `words.json` (код и объяснение — `references/audio-pipeline.md`); без
     этого субтитры/поиск дублей увидят рваные фрагменты вместо слов.
   - **`groq`** — `scripts/transcribe_groq.py <video> words.json --language ru` (без `--language`
     Groq сам определит язык). Сам режет длинный файл на куски по реальным паузам и склеивает
     результат — вызывать один раз на весь ролик, отдельная нарезка не нужна (и отдельно решать
     вопрос тишины-зацикливания не нужно — Groq отдаёт готовые слова, не токены, проблемы BPE тоже
     нет). Перед вызовом предупреди коротко, что это платный API-запрос (не «качаю модель разово»,
     а «трачу твои Groq-кредиты сейчас»). Результат — тот же формат `words.json`, дальше пайплайн
     не отличается независимо от движка. Подробнее — `references/transcription-groq.md`.
2. **Поиск дублей/фальстартов** — сначала запусти `scripts/find_repeat_candidates.py words.json`
   (структурный предфильтр — находит и точные повторы, и ЧАСТИЧНЫЕ/префиксные совпадения:
   человек может запнуться на полуслове и начать заново НЕСКОЛЬКО раз с РАЗНОЙ длиной оборванной
   фразы каждый раз — например «чувак я» / «чувак я» / «чувак, я даже не думал...» — три попытки
   разной длины, дословно ни одна не повторяет другую, чистый n-gram такое не ловит, а этот скрипт
   ловит). Затем прочитай ВЕСЬ `words.json` из шага 1 сам (ты — та же модель, что выполняет эту
   задачу у нас в проде через `claude -p`; не пролистывай по диагонали — этот шаг легко молча
   пропустить или свернуть). Список кандидатов от скрипта — ПОДСКАЗКА, не готовый вердикт: держи
   его перед глазами, чтобы короткие обрывки не потерялись на длинном транскрипте, но окончательное
   решение (резать/не резать, где именно граница) всегда за твоим прочтением и правилами ниже —
   скрипт не понимает смысл, может и пропустить реальный дубль, и предложить лишнее.

   **Метод — по смыслу, не по словам.** Разбей текст на смысловые единицы (предложения/законченные
   мысли), не на паузы. Два типа дублей:
   - **Фальстарт** — фраза ЯВНО оборвана/оговорка И сразу следом та же мысль начинается заново
     почти теми же словами (как раньше) — включая случай НЕСКОЛЬКИХ последовательных обрывов
     подряд с разной длиной каждого (см. пример выше) — режь ВСЕ обрывки, не только соседнюю пару.
   - **Смысловой повтор** — два соседних (или близких) предложения говорят ОДНО И ТО ЖЕ с сильным
     совпадением слов/формулировки. Люди обычно не повторяют одну и ту же мысль дважды подряд без
     причины — если это произошло, это почти всегда дубль дубля, а не два разных предложения.
     **Исключение — явный маркер повтора** («повторюсь», «скажу ещё раз», «повторю ещё раз» и
     похожие) — если спикер САМ обозначил, что повторяется намеренно, это НЕ дубль, не режь.
   - Когда нашёл дубль (любого типа, в т.ч. цепочку из 3+ обрывков) — **режь ВСЕ более ранние
     попытки, оставляй ТОЛЬКО ПОСЛЕДНЮЮ** (не «наверное», а правило: последний дубль = финальная,
     самая отточенная версия мысли).

   **Правило — ошибайся в сторону сохранения**: лишний лёгкий повтор не страшно оставить, а
   вырезать осмысленную фразу/шутку/панчлайн недопустимо; сомневаешься — не режь (пустой список это
   нормальный результат). НИКОГДА не режь: сатиру (голосом персонажа/пародия → потом своё мнение),
   приём завязка→панчлайн, нагнетание повтором для акцента, перефразировку той же мысли ДРУГИМИ
   словами (разные слова = не дубль, даже если смысл близкий) — только когда совпадение слов
   реально высокое.

   **Результат — ПАРЫ ИНДЕКСОВ слов, не тайм-коды.** `{"pairs": [[dropIdx, keepIdx], ...]}` (пустой
   список, если дублей нет), сохрани как `pairs.json`. `dropIdx` — индекс ПЕРВОГО слова самой ранней
   отбрасываемой попытки, `keepIdx` — индекс ПЕРВОГО слова версии, с которой продолжаем (для цепочки
   из 3+ обрывков — ОДНА пара на всю цепочку: dropIdx самого первого обрывка, keepIdx финальной
   чистой версии, не пара на каждый обрывок). `find_repeat_candidates.py` уже даёт `start_idx` для
   каждого вхождения — не пересчитывай индекс по транскрипту вручную, бери оттуда. **Почему не
   тайм-коды слов напрямую:** DTW-таймкод (`word.start`) запаздывает относительно реального начала
   звука на 0.2-0.8с (измерено) — резать по нему оставляет хвост выброшенного слова в кадре
   («чтобы… чтобы»). Индексы разрешает в точные границы следующий шаг. Подробности —
   `references/audio-pipeline.md`.

   **Согласование с пользователем.** Проверь маркер `retake-review:` в шапке `assets/stylekit.ts`
   (тот же файл и механика, что для стиля в Шаге 4):
   - `retake-review: ask` (дефолт, ещё не спрашивали в этом проекте) — покажи пользователю список
     найденных дублей (текст, ПРИБЛИЗИТЕЛЬНОЕ время по `word.start`, какую версию оставляешь — точная
     граница реза появится только после Шага 6 п.3) и дай подтвердить или поправить список перед
     вырезанием, не режь молча. Одновременно спроси: «на следующих видео в этом проекте так же
     показывать дубли на согласование, или сразу резать и просто сообщать?» — и запиши ответ,
     заменив строку `retake-review:` в шапке `stylekit.ts` на `ask` или `auto` соответственно (не
     переспрашивай в этом проекте повторно после этого).
   - `retake-review: auto` (пользователь уже выбрал не согласовывать) — режь сразу, но всё равно
     **вслух скажи итог** (например: «нашёл 3 дубля на 0:12, 1:04, 2:30, оставил последние версии»
     или «дублей/фальстартов не нашёл, всё чисто») — это единственный шаг без скрипта, который
     проверяет результат, пользователь должен видеть, что он реально произошёл, а не был молча
     пропущен или свёрнут до пустого списка.
3. **Границы реза — по реальной речевой активности, не по сырым тайм-кодам слов.** Заведи рабочую
   папку (`workDir`, например `.montage-work/` рядом с проектом), извлеки моно 16кГц wav туда как
   `audio16k.wav` (`ffmpeg -i <video> -vn -ac 1 -ar 16000 workDir/audio16k.wav`). Дальше, только
   если `pairs.json` из шага 2 непустой (пустой список — этот шаг и следующий абзац пропусти, дублей
   резать нечего):
   ```bash
   python3 scripts/vad.py workDir/audio16k.wav workDir/vad.json
   node scripts/refine_cuts.mjs workDir words.json pairs.json retakes.json
   ```
   `vad.py` строит карту речевой активности (адаптивный порог по локальному шуму + гистерезис, ловит
   межсловные щели, которые грубый `silencedetect` пропускает). `refine_cuts.mjs` для каждой пары
   индексов ставит границу реза: если рядом есть реальная пауза (по карте VAD) — граница = середина
   этой паузы (точно); если фальстарт произнесён СЛИТНО с предыдущей фразой без паузы — граница =
   локальный минимум энергии между словами (приблизительно, честный предел метода — см.
   `references/rendering-sequence.md`, там же что сказать пользователю в этом случае). Лог показывает,
   каким способом поставлена каждая граница (`pause`/`energy-min`) — это и есть проверяемость, не
   «на слух». Результат — `retakes.json` с уже правильными временными границами (не сырыми
   `word.start`). Подробности и почему это нужно даже поверх `snap_cut_boundaries()` в
   `cut_silence.py` — `references/audio-pipeline.md`.
4. **Монтаж и рендер — план без переэнкода, рекомендуемый путь.**
   ```bash
   PRESNAPPED=1 GAP=0.8 node scripts/plan_cut.mjs workDir words.json retakes.json workDir/plan.json
   ```
   **`PRESNAPPED=1` ОБЯЗАТЕЛЕН**, если `retakes.json` пришёл из Шага 6 п.3 (`refine_cuts.mjs`) —
   без флага `plan_cut.mjs` применит СВОЮ собственную грубую DTW-lag коррекцию поверх уже правильных
   границ и испортит их (проверено — без флага результат хуже, чем если бы `retakes.json` вообще не
   передавали). **`GAP=0.8`** — переопределяет встроенный дефолт скрипта (1.5с) значением, уже
   выверенным этим скиллом для разговорной речи (см. `--gap 0.8` в старом пути ниже). `retakes.json`
   — обязательный аргумент, ОПУСКАТЬ его нельзя (упадёт без файла); если `pairs.json` из Шага 6 п.2
   был пустым списком (дублей не нашлось — Шаг 6 п.3 в этом случае пропущен целиком), просто запиши
   `{"cuts": []}` в `retakes.json` сам, скрипт всё равно порежет длинные паузы через свой встроенный
   `longSil`.

   Если делал leveling голоса — прогони `scripts/clean_audio.py <video> --render workDir/leveled.mp4`
   на ИСХОДНОМ видео ДО этого шага (не после — тут нет отдельного «после реза» файла), используй
   `leveled.mp4` как источник ниже вместо сырого.

   `plan_cut.mjs` печатает автопроверки — **прочитай вывод, не просто проверь код возврата**: если
   видишь `VERIFY FAILED` (повтор слова на стыке — ровно дефект «чтобы… чтобы», если границы
   почему-то не разрешились), скажи об этом пользователю, не отдавай молча. `words kept: N of M` —
   если N заметно меньше M не из-за реальных вырезанных дублей/пауз, а из-за подозрительной потери —
   тоже стоит перепроверить.

   Собери композицию `<Sequence>`+`<OffthreadVideo trimBefore/trimAfter>` по `plan.json` вместо
   физической резки видео — код, почему это устраняет рассинхрон звука/картинки (было 0.86с на 48
   стыках у cut+concat, стало 0.04с), и цена (память компоновщика на телефонных `.MOV` + проверенный
   фикс через прокси) — `references/rendering-sequence.md`. `SubtitleTrack` в следующем шаге берёт
   слова прямо из `plan.words` — уже на новом таймлайне, ничего пересчитывать не нужно.

   **Альтернатива (legacy) — один физический mp4-файл через `cut_silence.py`.** Если по какой-то
   причине нужен именно отдельный смонтированный файл (не Remotion-композиция) —
   `scripts/cut_silence.py <video> <words.json> <out.mp4> <out_words.json> --audio --gap 0.8
   --pad 0.15 --level --cut-spans retakes.json` (тот же `retakes.json` из Шага 6 п.3 — сырые
   тайм-коды сюда передавать НЕЛЬЗЯ по той же причине, что и в `plan_cut.mjs`; `--level` тут
   по-прежнему работает ПОСЛЕ реза, как раньше). При числе сегментов больше ~20 — предупреди
   пользователя о риске рассинхрона и проверь потоки (`ffprobe -show_entries
   stream=codec_type,duration`) перед тем, как отдавать файл финальным. Слова у вырезанных дублей
   теперь корректно ВЫБРАСЫВАЮТСЯ (`drop_words_in_cuts()`), а не примагничиваются к границе реза —
   раньше это давало фантомные субтитры (7 слов схлопывались в 0.05с на реальном материале).
5. **Субтитры** — используй `assets/primitives/SubtitleTrack.tsx` (`<SubtitleTrack words={...} />`
   как оверлей поверх композиции; значения — `plan.words` из Шага 6 п.4 при Sequence-рендере, или
   `cut_words.json` при legacy-пути — в обоих случаях слова уже на новом таймлайне, ни одно не
   потеряется на вырезанных паузах/дублях). Это наш выверенный karaoke-компонент (группировка по 3
   слова/паузе >0.7с/2.8с максимум на экране, активное слово подсвечено плашкой) — НЕ используй
   дефолтную стилистику официального `/remotion-captions` для самого рендера субтитров, она даёт
   рубленые, слишком короткие фрагменты без нашей группировки. `/remotion-captions` можно звать
   только чтобы ПОЛУЧИТЬ субтитровый файл/структуру данных, если она вдруг понадобится отдельно —
   не для финального визуала.
6. **Улучшение голоса** — если не сделал на Шаге 6 п.4 (Sequence-путь, до `plan_cut.mjs`) и не
   флагом `--level` (legacy-путь), отдельно `scripts/clean_audio.py <video> --render <out>`.
   Диагностирует и чинит только то, что реально сломано (шум/громкость/клиппинг) — не гарантированно
   «улучшает» звук вслепую, это осознанно.
7. **Графика — по режиму, выбранному на Шаге 5.**
   - **Автоматически** — прогони расшифровку через словарь «маркер речи → примитив»
     (`references/marker-action-library.md`, реализация примитивов — `references/primitive-map.md`,
     сами компоненты — `assets/primitives/`) и **сформулируй конкретно 1-3 места с конкретной
     графикой** («на 0:14, где ты говоришь про рост в 3 раза — предлагаю countUpNumber») — этот
     шаг нельзя молча пропустить и нельзя заменить общим «нужна ли графика?». Дай пользователю
     решить, какие вставки брать.
   - **Без графики** — пропусти этот пункт целиком, ничего не предлагай.
   - **Пользователь диктовал сам** — реализуй накопленный на Шаге 5 список требований, по одному
     пункту, не изобретай ничего сверх списка.
8. **Финальный рендер — НЕ сразу.** Не рендери молча, как только графика готова: сначала пройди
   Шаг 7 целиком (отчёт → превью → подтверждение) ниже, финальный экспорт в файл — его последнее
   действие, а не это. Если видео снято на телефон (частый случай — talking-head) и рендер падает
   по памяти компоновщика — прокси-транскод с частыми опорными кадрами, см.
   `references/rendering-sequence.md`.

## Правило: новый примитив ИЛИ целая сцена — всегда предлагай занести в банк насовсем

Если по ходу работы (не только на первом видео — в любой сессии) пользователь попросил что-то,
чего нет в `assets/primitives/`, и ты нарисовал компонент с нуля под его конкретный запрос —
**ИЛИ собрал вместе с ним целую сцену** (составную композицию из нескольких примитивов/переходов,
не сводится к одному файлу) — **всегда спроси, сохранить ли это насовсем**, а не только для
этого ролика. Не жди, что пользователь сам догадается попросить — задай вопрос прямо
(«получилось неплохо — сохранить как постоянный [примитив в банке / пример сцены], чтобы
предлагать его и в следующих видео?»).

- Если это ОДИН компонент — положи файл в `assets/primitives/`, добавь запись в
  `references/primitive-map.md` (props, когда уместен) и, если подходит под существующую семью —
  в `references/marker-action-library.md`.
- Если это ЦЕЛАЯ СЦЕНА (несколько примитивов вместе) — сохрани композицию как отдельный пример в
  `assets/scenes/<короткое-имя>.tsx` (папки может не быть — создай), с комментарием сверху, из
  чего она собрана и когда уместна. Отдельного реестра под сцены пока нет — этого формата
  достаточно, дальше решим по мере накопления примеров.

Банк растёт от реального использования, не только от того, что заложено при сборке скилла —
**подскажи сам, что так можно, а не жди, пока пользователь захочет что-то нестандартное.** Когда
уместно (например, на Шаге 4 про стиль/экскурс возможностей, или если видно, что ни один примитив
банка не подходит под задачу) — намекни: «если есть скриншот или схема с графикой, которая
нравится (референс, не обязательно из видео) — пришли, я попробую отрисовать похожий примитив,
доведём его до ума и сохраним в банк как обычный». Не только цвета/шрифты тянутся из референсов —
новый примитив тоже можно собрать с картинки, не только по словесному описанию.

## Шаг 7. Итоговый отчёт → превью → подтверждение → и только потом финальный рендер

**Нельзя пропускать молча** (см. вступление) — не делай финальный экспорт в файл сразу после
графики без этого шага, даже если по ощущению «и так всё понятно».

1. **Собери короткий отчёт по всем решениям пайплайна**, одним компактным сообщением (по
   пунктам, не простынёй):
   - **Дубли/фальстарты** — что нашёл на Шаге 6 п.2 (`pairs.json`), какую версию оставил, точные
     границы — из `retakes.json` после Шага 6 п.3 (`refine_cuts.mjs`). Если список пуст — так и
     скажи («дублей не нашёл, всё чисто»). Если хоть одна граница поставлена по `energy-min`, а не
     `pause` (`refine_cuts.mjs` помечает это в логе каждой строкой) — упомяни коротко, что в этом
     месте фальстарт слитный и граница приблизительная (это честный предел метода, не ошибка —
     см. `references/rendering-sequence.md`), не обещай идеальный шов там, где его физически нет.
   - **Паузы и общая длительность** — при Sequence-пути (`plan_cut.mjs`) возьми готовую сводку из
     его вывода (число сегментов, итоговая длительность, `words kept: N of M`) и посчитай разницу
     с исходной длительностью как «вырезано суммарно» — не пересчитывай вручную. При legacy-пути
     `cut_silence.py` печатает это явно (секунды на паузы отдельно от секунд на дубли/ретейки) —
     возьми оттуда.
   - **Графика** — какие примитивы предложены/выбраны и на каких таймингах (из Шага 6 п.7, или
     накопленный список пользователя, если он диктовал сам).

2. **Проверь маркер `final-review:` в шапке `assets/stylekit.ts`** (та же механика, что
   `retake-review:` для дублей на Шаге 6 п.2):
   - `final-review: ask` (дефолт, ещё не спрашивали в этом проекте) — покажи отчёт из п.1, запусти
     превью (см. платформенные варианты ниже) и спроси: «всё ок — рендерим финал, или что-то
     поправить?». Дай пользователю попросить точечную правку (переделать конкретный кусок/примитив/
     тайминг), не только принять или отклонить целиком — не переходи к финальному рендеру, пока
     не подтвердил явно. Заодно спроси: «на следующих видео в этом проекте так же показывать отчёт
     и спрашивать, или сразу рендерить и просто сообщать итог?» — и запиши ответ, заменив строку
     `final-review:` в шапке `stylekit.ts` на `ask` или `auto` соответственно (не переспрашивай
     в этом проекте повторно после этого).
   - `final-review: auto` (пользователь уже выбрал не согласовывать) — не жди подтверждения, но
     всё равно **вслух покажи отчёт из п.1** перед тем как рендерить (одной короткой репликой) —
     тот же принцип, что и `retake-review: auto`: результат должен быть виден, а не молча
     проскочен.

3. **Превью** (запускай в режиме `ask` до вопроса о подтверждении; в режиме `auto` — по желанию,
   не обязательно, раз пользователь уже сказал не ждать):
   - **Claude Desktop (вкладка Code)**: запусти `npx remotion studio`, dev-сервер откроется прямо
     в Browser-панели приложения — ничего дополнительно открывать не надо.
   - **Claude Code в терминале**: `npx remotion studio`, дай пользователю открыть выведенный адрес
     в браузере самому.
   - **Codex**: своего превью-окна нет — тот же `npx remotion studio`, но адрес нужно открыть в
     обычном браузере пользователя руками, агент это увидеть не может.

4. **Финальный рендер/экспорт в файл** — только теперь, после подтверждения (`ask`) или сразу
   после короткого итога (`auto`). Это последнее действие пайплайна.

## Если ошибка/жалоба/идея — предложи написать автору напрямую

Это НЕ CTA под каждым сообщением и не промо — предлагай только когда реально есть повод:
- шаг падает с ошибкой, которую не получается починить самому по докам этого репозитория
  (`references/*.md`, докстринги скриптов) — застрял, а не просто долго разбираешься;
- пользователь явно недоволен результатом (жалоба на качество монтажа/субтитров/паузы и т.п.);
- пользователь предлагает идею/просит функцию, которой в скилле нет.

В такой момент — одной короткой фразой, не навязчиво: «если хочешь, можешь описать это напрямую
автору скилла — https://t.me/a_prisekin (баг, идея, жалоба — что угодно), он читает лично».
Не повторяй это в каждом ответе и не превращай в подпись — только по делу, когда правда есть о
чём писать.
