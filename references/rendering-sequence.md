# Монтаж без переэнкода — `<Sequence>` + `trimBefore` вместо cut+concat

## Проблема, которую это решает

`cut_silence.py`'s `cut_video()` кодирует каждый оставшийся кусок отдельно (memory-light, специально
так — filter_complex одним проходом валится по памяти на длинных роликах, см. ниже) и склеивает
concat-демуксером. Аудио округляется по кадру AAC (1024 отсчёта ≈ 21.3мс), видео — по 1/30с (33.3мс).
Округления разные, расхождение копится на каждом стыке.

Измерено на реальном ролике с 48 сегментами: расчётная сумма сегментов 82.393с, реальное аудио
84.149с, реальное видео 85.049с — **0.86с расхождения A/V**, ~18мс на стык. На малом числе сегментов
(9, как в первом тестовом ролике) это даёт 0.4с и проходит незамеченным; на 48 — звук уезжает почти
на секунду, и субтитры (рассчитанные на 82.4с) прогрессивно расходятся с видео (85с).

## Минимальный фикс (если остаёшься на cut_silence.py)

При числе сегментов больше ~20 — предупреди пользователя и проверь потоки после резки:
```bash
ffprobe -v error -show_entries stream=codec_type,duration -of csv=p=0 cut.mp4
```
Если аудио- и видео-потоки разошлись заметно (>0.1с) — не отдавай этот файл как финальный, это и
есть дефект выше, не что-то, что можно доправить постфактум.

## Правильное решение — план монтажа как данные, без пересборки исходника

Не резать файл вообще. `scripts/plan_cut.mjs` не трогает медиа — он читает `words_cut.json`
(word-level таймкоды, уже скорректированные `fix_word_times.py`+`snap_cuts.py`) и `retakes.json`
(границы дублей, `refine_cuts.mjs`+`snap_cuts.py` — см. `audio-pipeline.md`, раздел про
VAD/фальстарты) и считает JSON-план: какие куски ИСХОДНОГО файла
оставить (`segments`), на каких таймкодах нового таймлайна они окажутся (`offsets`), и слова,
пересчитанные на новый таймлайн (`words`) — плюс сам себя проверяет (см. «Автопроверки» ниже).

Remotion потом играет эти куски ПРЯМО ИЗ ИСХОДНИКА — стыков как физического объекта не существует,
значит и рассинхрону неоткуда взяться:

```tsx
import { Sequence, OffthreadVideo } from "remotion";
import plan from "./plan.json";

const FPS = 30;

export const EditedVideo: React.FC = () => (
  <>
    {plan.segments.map(([start, end]: [number, number], i: number) => {
      const durationInFrames = Math.round((end - start) * FPS);
      const from = Math.round(plan.offsets[i] * FPS);
      return (
        <Sequence key={i} from={from} durationInFrames={durationInFrames}>
          <OffthreadVideo
            src={staticFile("source.mp4")}
            trimBefore={Math.round(start * FPS)}
            trimAfter={Math.round(end * FPS)}
          />
        </Sequence>
      );
    })}
  </>
);
```

Расхождение A/V на том же материале с этим подходом — 0.04с вместо 0.86с (Remotion рендерит
покадрово и сам сводит звук — по построению, не постфактум). Побочно бесплатно получаются
кроссфейды между сегментами (наложи соседние `<Sequence>` на несколько кадров с fade).

`SubtitleTrack` берёт слова из `plan.words` (уже на новом таймлайне) — ничего дополнительно
пересчитывать не нужно, тот же контракт, что раньше был у `cut_words.json`.

### Куда девать `--level` (выравнивание голоса)

`clean_audio.py` раньше запускался НА УЖЕ ВЫРЕЗАННЫЙ файл (`_level_audio()` внутри
`cut_silence.py`, после конкатенации). В Sequence-подходе отдельного вырезанного файла нет —
прогони `clean_audio.py <source> --render <leveled_source>` на ИСХОДНОМ файле ДО `plan_cut.mjs`,
и используй `leveled_source` как `src` у `<OffthreadVideo>` вместо сырого исходника. Результат
эквивалентен (статическое выравнивание громкости не зависит от того, что вырезано — те же сэмплы,
просто на новом таймлайне) и даже проще (один проход по всему файлу, а не по уже нарезанным кускам).

### Тупик, в который не надо ходить

Собрать тот же рез одним проходом `filter_complex` (N веток trim + concat-фильтр) вместо посегментного
кодирования в `cut_silence.py` — падает по памяти: каждая ветка декодирует весь файл независимо.
Посегментное кодирование в `cut_silence.py` выбрано осознанно и правильно для СВОЕГО случая
(докстринг так и говорит — «memory-light»); Sequence-подход решает ту же проблему иначе — не через
меньше памяти на кодирование, а через отказ от кодирования вообще.

## Цена Sequence-подхода — память компоновщика на телефонных .MOV

Remotion дёргает исходник вразнобой в десятках мест по таймлайну (не последовательно, как при
обычном проигрывании). На телефонных `.MOV` с редкими опорными кадрами (keyframe раз в ~29 кадров)
каждая перемотка декодирует от далёкого опорного кадра — на ролике с 41 сегментом компоновщик упал:

```
Compositor exited with code 3221226505: memory allocation of 2764854 bytes failed
```

**Проверенное решение — прокси с частыми опорными кадрами** плюс ограничение параллелизма/кэша на
рендере:
```bash
ffmpeg -i src.mov -c:v libx264 -crf 19 -preset veryfast \
  -g 15 -keyint_min 15 -sc_threshold 0 -pix_fmt yuv420p \
  -c:a aac -b:a 192k -movflags +faststart -y proxy.mp4
```
```bash
npx remotion render ... --concurrency=2 --offthreadvideo-cache-size-in-bytes=536870912
```
Используй `proxy.mp4` как источник для `<OffthreadVideo>` вместо сырого `.MOV`, если видео снято на
телефон (частый случай для этого скилла — talking-head с телефона). Обычные видео с уже частыми
опорными кадрами (screen recordings, экспорт из монтажки) эту проблему обычно не показывают — прокси
не универсально обязателен, только когда компоновщик реально падает или источник — телефонный `.MOV`.

## Что нельзя решить, и это стоит сказать пользователю прямо

Фальстарт, произнесённый СЛИТНО с предыдущей фразой без паузы («…выбирает особые позы, чтобы ничего
её, чтобы ничего не торчало» — между «позы,» и «чтобы» паузы нет физически) — границу ставить не по
чему: ни пороговый детектор, ни VAD (`vad.py`), ни нейросеть тут не помогут, разделять нечего.
Единственная зацепка — локальный минимум речевой активности между словами (`refine_cuts.mjs` делает
это как fallback, помечает лог-строку `prob-min`/`prob-plateau+energy-min` на движке Silero или
`energy-min` на энергетическом fallback вместо `pause`), и это по определению приблизительное место,
не точная граница — сигнал стал точнее (речевая вероятность вместо голой энергии), но природа
ограничения не изменилась. На реальном материале таких мест было 4 из 52 (сглаживаются коротким
кроссфейдом на стыке). Если пользователь слышит лёгкий шов именно в таком месте — это предел метода,
не недоделка; стоит сказать это прямо, а не обещать идеальный результат в каждом случае. Открытый
вопрос (не разрешён, не переписывать этот раздел без данных) — действительно ли между ЛЮБЫМ
самоисправлением есть физиологический микроразрыв (закрытие гортани/вдох), который более
чувствительный детектор со временем найдёт, или в части случаев разрыва нет вообще; проверять на
реальных «слитных» кейсах по мере накопления материала.

## Автопроверки — встроены, не молчат

`plan_cut.mjs` сам проверяет и печатает шесть инвариантов (V1-V6, подробности механизма —
`audio-pipeline.md`):
- **V1 — повтор слова на стыке** — последнее слово перед резом не должно совпадать с первым словом
  после (это ровно дефект «чтобы… чтобы» из-за DTW-лага) — `VERIFY FAILED`, если нашёл.
- **V2 — вырезанный дубль реально отсутствует в финале** — ни один спан из `retakes.json` не
  пересекается с итоговыми сегментами (раньше дубли короче ~0.8с молча возвращались проходом
  слияния сегментов — почти любой реальный фальстарт короче этого).
- **V3 — ни одно акустически подтверждённое слово не потеряно паузой** (защита слов через
  `support[]`, см. `audio-pipeline.md`) — `VERIFY FAILED`, если сработало, не должно случаться
  никогда при исправной карте.
- **V4 — информационно, не ошибка** — список слов без акустического подтверждения, удалённых вместе
  с паузой: подозрение на галлюцинацию ASR на тишине (реальный случай — Whisper повторил одну фразу
  ~70 раз на длинном тихом ролике, см. `audio-pipeline.md`), не баг этого шага.
- **V5 — разбивка `words kept`** по причине (оставлено / удалено ретейками / удалено как
  неподтверждённое / удалено по иной причине) вместо одной непроверяемой цифры — раньше на
  реальном материале дважды теряли слова молча (23 разом из-за фильтра коротких сегментов, 21 из-за
  привязки слова к сегменту по середине вместо начала).
- **V6 — сохранённое слово не обрезано резом** — слово, попавшее в категорию «оставлено», должно
  целиком (с допуском `PAD`) лежать внутри своего сегмента, а не только стартовой точкой. Ловит
  ситуацию, когда граница реза из `retakes.json`/пауз прошла посреди слова (см. дефект
  «ткани»/«интересней», найденный на реальном материале 2026-08-29, `CHANGELOG.md`) — то, что
  `plan_cut.mjs` раньше принимал границы `retakes.json` как данность и не перепроверял их сам.
  Сравнивает с меньшим из сырого `end`/старта следующего слова/акустически подтверждённого
  интервала (2026-09-02) — раздутый Whisper'ом `end` иначе даёт ложные срабатывания.
- **V7/V8 (2026-09-02, информационные, НЕ роняют `VERIFY FAILED`)** — кусок речи внутри сегмента
  без единого слова / слово, чей таймкод пересекает паузу длиннее 0.4с. Ловят класс дефекта, где
  Whisper слил лишний заход в соседнее слово и текстового дубля не осталось вообще — пока не
  подтверждены живым тестом, поэтому только предупреждают, не блокируют.

Дополнительно, вручную/отдельным вызовом — длительность потоков после Remotion-рендера не должна
расходиться больше чем на ~0.1с (`ffprobe`, см. «Минимальный фикс» выше) — тот же чек, что и для
legacy-пути, но здесь как sanity-check финального рендера, а не диагностика самой резки.
